# Gateway 请求超时不得破坏通道

## 约束与原因

普通 RPC 超时只结束对应调用，不应广播连接故障或关闭通道。连接存活由协议心跳管理，
实际底层关闭、协议损坏、权限撤销和显式关闭另行处理。2026-09-11 的 RTC 日志证明
固定 5 秒组包期限会截断仍在传输的消息，见 `../40-runbooks/webrtc-relay-fragment-timeout.md`。

CPG1 使用单个可靠有序 DataChannel，消息不能交错。调用超时不等于传输取消：已经开始
的消息必须继续完整收发；迟到响应按请求 ID 丢弃。不可清空部分消息后把尾部分片当成
新消息，也不可让发送 future 的超时造成两个发送任务并行。保留消息及队列内存上限。

## 回归验证

- 超过旧组包期限的有效消息仍能完成。
- 超时请求的迟到响应不会失败其他请求或事件流。
- 部分发送遇到背压且调用超时后，恢复发送仍保持消息顺序。
- 必须覆盖共用 session writer；不能只测试 RTC 适配器。模拟发送跨过 30 秒调用期限，
  验证无通道失败通知、顺序不变，且显式会话清理仍能取消阻塞发送。
- 真正心跳失效能驱动重连，关闭能释放待处理请求和组包状态。
- 同时覆盖 Host 接收、Remote 接收和 LAN，不能只修改一个方向。

心跳与业务共用有序通道时仍有排队风险；需要通过慢速大消息与心跳并发的真机验证评估，
不能把移除业务超时断联等同于保证任何吞吐条件下都在线。
