1. 结论边界：两个接口不能混为一个根因

高置信实测

拉取历史消息：用户推断成立

Shell、读文件、搜索、日志抓取、diff 等操作文本是响应体的主要组成。最大真实页面约 14.4 MiB，其中 command item 约占 92%，已经逼近 16 MiB 硬上限。

2. 调查方法、环境与尺寸口径

2.1 三层证据

  1. 真实读取 调用本机 Context Provider 的 list_threads 与 read_thread，抽取现存历史；对同一页面分别读取 includeOutputs=true/false，直接计算工具正文增量。
  2. 真实黑盒 启动 /Applications/Code Pet.app 包内的 codepet-provider-codex，仅通过公开 Provider JSON-RPC 执行 initialize、instance.create/start、conversation.list/get、stop/shutdown。使用真实本机历史，不调用内部 Rust 对象。
  3. 离线模拟 对已取得的真实 JSON 响应做内存副本变换，模拟“截断”和“去重”后的序列化大小。模拟没有改变 App、Provider、历史文件或仓库代码。

2.2 计量口径

  • 表中的 bytes 均按 UTF-8 JSON 紧凑序列化计算。
  • MiB 使用 1,048,576 bytes；KiB 使用 1,024 bytes。
  • 黑盒 conversation.get 数值主要统计 result，实际 Provider JSON-RPC frame 还会增加 envelope，因此必须保留安全余量。
  • Context Provider 的 read_thread 单次最多 10 turns、单 item 输出最多 20,000 chars；它天然比 Code Pet Provider 的 256 KiB 单工具文本上限更保守。

这一现象不能只归因于 Codex Mapper “写了几遍”。Schema 同时允许 contents、tool.input、tool.rawInput、tool.command、tool.result.content 和 tool.result.structuredContent 持有完整载荷，却没有规定唯一事实源、互斥关系或引用关系。Mapper 的重复是表象，对象模型的多权威设计才是系统性诱因。

7. 对象设计复盘：问题不是“字段多”，而是“同一事实有多个所有者”

修正后的架构判断：ToolInvocation 这个抽象本身是必要的；不合理的是它与 ConversationItem.contents 发生了完整正文所有权重叠，而且 tool 内部又有第二轮重叠。当前协议没有建立 single source of truth，因此服务端、客户端、截断器和增量同步各自选择不同字段都算“合法”，最终必然出现重复、分歧和补丁式 fallback。

7.1 五组重叠分别意味着什么

重叠组当前可承载的事实真实案例设计缺陷
ConversationItem.contents ↔ ToolResult.content工具输出正文案例 A 的 801 条 output 在两处逐字相等，额外复制 5,719,156 B展示层内容与领域对象结果都拥有全文，没有 canonical owner

7.2 为什么可以确认是协议级问题，而不只是 Codex 实现错误

Codex / OpenCode

相同 Schema 诱导出相同重复

Codex command mapper 同时填充顶层 command/output 和 tool input/result/command；OpenCode 的 shell mapper 也采用同样的双层填充。这说明重复不是某一行手误，而是多个实现都在满足两个看似独立、实则重叠的消费模型。

Claude

另一实现选择了另一权威位置

Claude 的 tool_use 映射把 contents 留空，主要数据放进 ToolInvocation。它证明顶层副本并非协议运行所必需，也暴露出跨 Provider 语义不一致：客户端不能从 Schema 得知正文一定在哪里。

代码位置：Codex crates/providers/codepet-provider-codex/src/mapper.rs:600–689；OpenCode crates/providers/codepet-provider-opencode/src/mapper.rs:369–397, 848–898；Claude crates/providers/codepet-provider-claude/src/provider.rs:2511–2583；协议定义 protocol/provider/v1/schema.json 的 ToolContent、ToolInvocation 与 ConversationItem。

7.3 重复不只浪费空间，还会产生正确性风险

风险当前证据可能表现
截断只改到一个副本fit_single_turn_conversation_history 只缩减 item.contents，不统一处理 tool input/result响应仍很大；时间线与详情抽屉看到的文本长度不同

两个副本发生内容漂移字段没有引用约束，也没有相等性校验某个 Mapper 修复、截断或脱敏一处后，另一处仍保留旧值
不同 Provider 行为不一致Codex/OpenCode 填双份，Claude 顶层 contents 为空客户端不断加入 provider-specific fallback，协议抽象失去价值

7.4 最终协议决策：用判别联合让非法组合无法出现

最终方案不是在投影器里做文本去重，也不是为了工具抽屉建立另一套详情对象，而是直接修改 Provider/Gateway v1：ConversationItem、tool input 和 tool outcome 都采用带 kind 的封闭 oneOf。每个分支只拥有自己合法的字段，命令与输出各只有一个 canonical 位置。项目尚未现场发布，因此两个协议与两端实现同步更新，版本号仍保持 v1。

{
  "resource": { "itemId": "exec-…", "conversationId": "…" },
  "kind": "tool",
  "status": "completed",
  "title": "Shell",
  "tool": {
    "callId": "exec-…",
    "name": "shell",
    "input": {
      "kind": "command",
      "command": "rg …",
      "cwd": "/workspace"
    },
    "outcome": {
      "kind": "success",
      "contents": [{
        "contentId": "exec-…:output",
        "kind": "text",
        "text": "<唯一一份 output preview>",
        "truncation": {
          "originalBytes": 142362,
          "retainedBytes": 8192,
          "strategy": "head-tail"
        }
      }],
      "exitCode": 0
    }
  }
}
  • ConversationItem 联合：message、reasoning、tool/command、file change、approval、unknown 分支互斥；不再由一个对象上的大量 optional 字段表达领域状态。
  • ToolInput 联合：command | structured | opaque 三选一。Command 是“语义上执行命令”，Structured 是已可靠解析的 JSON，Opaque 是无法可靠理解的输入；尺寸大不等于 opaque。
  • ToolOutcome 联合：success | failure 二选一。内容块是输出唯一所有者；结构化 JSON 作为一种内容块，不再同时写 text 与 structuredContent；错误 message 只保留短摘要。
  • 截断元数据属于内容：截断与抽屉无关。任意 UI 都读取同一内容块，并用 originalBytes、retainedBytes、strategy 显示它不完整。
  • Delta 指向 canonical content：继续使用 itemId + contentId；客户端 committed contentId 必须遍历各 item variant 的内容块，不能依赖文本相等。

7.5 实施边界：协议先行，Provider 必须最先截断

  1. 先在 Provider/Gateway v1 Schema 固定联合、唯一所有权与截断元数据，并生成 Rust/Dart/TypeScript SDK。
  2. Provider Mapper 按新类型输出单份正文；共享 Provider SDK 在 stdout JSON 序列化前执行内容预算、页软预算和最终 16 MiB frame 检查。
  3. Host/Gateway 按联合分支校验和投影。Host 的二次预算可以保护远程链路，但不能修复已经无法写出 stdout 的 Provider response。
  4. Remote 更新解码、分页、committed contentId 和 delta 合并；消息内折叠或抽屉都只是同一 canonical 内容的视图。
不能采用的伪修复：只在 Mapper、Host 投影器或 Remote 做文本去重都不能从类型上排除双写；Remote 去重也无法避免 Provider 的 stdio JSON frame 先超限。只开 WebSocket 压缩不影响 Provider 进程间帧；只截断顶层 contents 会留下 tool 内全文；为抽屉建立第二份详情 payload 会重新制造双权威。

8. 当前代码为什么会产生这种结果

代码事实

工具文本普通上限为 256 KiB

bounded_tool_text 只在单段字符串超过 256 KiB 时截断。真实最大项多在 65–142 KiB，因此不会触发。

crates/providers/codepet-provider-codex/src/mapper.rs:1154

代码事实

结构化输入同样允许 256 KiB

工具 input 的 JSON 小于等于 256 KiB 时完整进入 structured_content/input；更大时才转换成截断文本。

crates/providers/codepet-provider-codex/src/mapper.rs:1006

代码事实

32 KiB 补救只在 limit=1 生效

fit_single_turn_conversation_history 在请求 limit 不是 1 时直接返回原响应；limit=1 仍超限才缩减 item.contents。

代码事实

Remote 默认先请求 40 turns

只有收到 provider_response_too_large 后才将 limit 减半；意味着先承受一次大响应构建与失败，再重试 20/10/5/2/1。

codepet-remote/lib/gateway/gateway_client.dart:545

边界问题：现有 32 KiB 补救只遍历 item.contents，没有统一预算 tool.input、tool.rawInput、tool.result.structuredContent 与 tool.result.content.text。因此对“正文在结构化 tool 中仍保留一份”的情况不够完整。

9. 建议方案：每一项对应什么真实案例

优先级 P0

建议 1：Remote 默认 history page 从 40 turns 降到 10

对应案例：案例 A 的相同起点，40 turns 为约 14.4 MiB，20 turns 为 6.51 MiB，10 turns 为 3.47 MiB，1 turn 为 44.9 KiB。

直接收益：首帧从约 14.4 MiB 降到 3.47 MiB，单帧下降约 76%，避免先构建超大帧、报错、再逐次减半。

代价：完整历史请求次数增加。Remote 当前最终仍会循环到全部分页并把 pages 合并到内存，因此该方案主要解决网络单帧与失败重试，不直接降低“完整历史最终内存”。

验证：使用案例 A 的 cursor 顺序回放，断言 10-turn pages 无重复、无遗漏、nextCursor 稳定；记录首屏可见时间与完整加载时间。

优先级 P0

建议 2：在 v1 协议层消除可共存的重复所有者

对应案例：案例 A 中 870 条命令的正文各出现 3 次；801 条输出各出现 2 次。精确重复正文至少 6,129,554 bytes。

模拟结果：仅删除与 contents 完全相等的 tool 正文副本，14.39 MiB → 8.40 MiB，下降 41.6%。

推荐协议：不是约定 Mapper “不要同时填写”，而是用 oneOf 让双写对象无法通过 Schema。command/structured/opaque input 三选一，success/failure outcome 二选一，完整结果只在 canonical content blocks；普通 user/assistant message 继续拥有自己的 blocks。

实施要求：协议与生成 SDK 先完成，Codex/OpenCode/Claude、Host/Gateway、Remote 再按同一合同并行迁移。Remote 工具详情与 command 时间线当前优先读取 tool.result，但 committed contentId 主要来自顶层 contents；新实现必须从判别分支遍历 canonical contentId，不能保留文本相等 fallback 作为长期机制。

优先级 P0

建议 3：操作文本使用 8–16 KiB 预览，不保留 256 KiB 默认正文

对应案例：最大 8 个真实工具输出为 65–142 KiB，全部绕过 256 KiB 上限；单项看似合理，累计后把一页推到 14.4 MiB。

截断方式：Shell/log/test 输出建议保留开头与结尾，而非只保留开头；末尾通常包含退出码、失败摘要和断言。内容块返回 truncation.originalBytes、retainedBytes、strategy=head-tail；文件 diff 可按文件拆分并给出文件级摘要。该元数据描述内容完整性，与内容是在消息内、抽屉还是详情页展示无关。

不应统一截断：用户消息和助手最终正文在样本中占比很小，应给予更高上限或独立策略，避免为了工具噪声损害主要对话内容。

优先级 P1

建议 4：建立整页 6–8 MiB 软预算，而不是只看单 item

对应案例：870 个 command 中没有任何一个必须超过 256 KiB，但总 command item 达约 13.9 MB。单项阈值无法约束累计体积。

行为建议：序列化前维护响应预算；优先保留 item identity、状态、标题、exitCode、timing、truncated/totalBytes，正文按剩余预算加入。达到软预算时不必丢弃整个 turn，也不应等到 16 MiB codec 才返回错误。

为什么是 6–8 MiB：案例 A 的 20-turn 页面为 6.51 MiB，说明这个区间既能承载大量真实 item，又为 Provider envelope、Gateway 转换和移动网络留出明显余量。

优先级 P1

建议 5：对 conversation.list 的 title/preview 单独设界

对应案例：172 条列表总计 358,761 bytes；最大单条 10,983 bytes，其中 title 与 preview 各 5,175 bytes。另一个样本 title 仅 43 bytes、preview 为 5,159 bytes，证明不能简单删除 preview。

建议：title 采用字符/字节上限（例如 1–2 KiB）；preview 采用独立 2–4 KiB 上限；当两者完全相等时只传一个权威值或加 previewSameAsTitle。保留 truncated/originalBytes。

边界：这会让列表更稳定，但不能把现有列表超限直接判定为已解决，因为当前实测列表页仅约 252 KiB。

优先级 P1

建议 6：增加接口级尺寸观测与错误归属

对应案例：列表 UI 报错不等于失败 RPC 一定是 conversation.list。Remote 的列表请求并不预取 conversation.get，因此需要日志明确记录 method、provider、cursor、limit、响应 bytes、item counts、重试次数和最终错误码。

建议字段：method、providerId、conversationIdHash、limit、cursorPresent、responseBytes、itemsByKind、truncatedBytes、deduplicatedBytes、retryFromLimit/toLimit。

隐私约束：日志只记尺寸和哈希，不记录完整命令、diff、用户正文或 tool result。

11. 已排除方向、未知项与下一步

已排除

  • “对话列表因为携带 Shell 原文而超限”：列表协议与本机实测均不支持该判断。
  • “只有某个超过 256 KiB 的巨型命令输出才会触发”：最大真实工具项均未触发 256 KiB 截断，累计已经接近 16 MiB。
  • “目前 32 KiB fallback 能覆盖所有工具字段”：代码只在 limit=1 且整帧过大时处理 item.contents，并非统一工具正文预算。
  • “重复只是 Codex Mapper 的单点实现错误”：OpenCode 也发生双层填充，而 Claude 选择另一种放置方式，说明 Schema 缺少唯一事实源和跨 Provider 约束。

仍未知

  • 未确认 用户现场“列表超限”对应的确切 RPC method、Provider、cursor 和 response size；需要尺寸日志或原始错误上下文。
  • 未确认 Claude/OpenCode 在本机真实大历史中的重复数据规模；代码路径已确认，但尚未做与 Codex 案例 A 同口径的黑盒量化。
  • 已决策 当前没有现场发布兼容负担，Provider/Gateway 继续使用 v1，Code Pet 与 codepet-remote 同步升级，不维护旧字段双栈。
  • 未确认 长列表在多个 Provider 并发请求时，UI 是否把其中一个失败统一展示成“列表加载失败”。

建议实施顺序

  1. 先修改 Provider/Gateway v1 的判别联合、唯一载荷所有权和截断元数据，并生成全部 SDK。
  2. Provider、Host/Gateway、Remote 以该协议为共同基线并行迁移；Provider 在 stdout 序列化前执行第一次预算。
  3. Remote 默认 limit 40 → 10，并为操作正文引入 8–16 KiB 语义预览和 6–8 MiB 页软预算。
  4. 加入只记尺寸、不记正文的接口观测，用真实 method 和 route 归因现场错误。
  5. 最后独立收口 conversation.list title/preview；两者相等是列表元数据冗余，不是 tool payload 的组成部分。
最终判断：历史消息尺寸问题已经有高置信、可量化的根因证据；对话列表目前只有“存在可优化的元数据冗余”证据，还没有“列表自身达到硬上限”的证据。实施时应拆成两个问题跟踪，避免用同一个截断开关掩盖错误归属。
