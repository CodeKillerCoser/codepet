2. 调查方法、环境与尺寸口径

2.1 三层证据

  1. 真实读取 调用本机 Context Provider 的 list_threads 与 read_thread，抽取现存历史；对同一页面分别读取 includeOutputs=true/false，直接计算工具正文增量。
  2. 真实黑盒 分别启动 /Applications/Code Pet.app 包内旧 Provider 和当前源码构建的新 Provider，仅通过公开 JSON-RPC 执行 initialize、instance.create/start、conversation.list/get、stop/shutdown。二者连接同一 CLI、读取相同 conversation/cursor/limit，不调用内部 Rust 对象。
  3. 离线模拟 对已取得的真实 JSON 响应做内存副本变换，模拟“截断”和“去重”后的序列化大小。模拟没有改变 App、Provider、历史文件或仓库代码。

2.2 计量口径

  • 表中的 bytes 均按 UTF-8 JSON 紧凑序列化计算。
  • MiB 使用 1,048,576 bytes；KiB 使用 1,024 bytes。
  • 黑盒 conversation.get 数值主要统计 result，实际 Provider JSON-RPC frame 还会增加 envelope，因此必须保留安全余量。
  • Context Provider 的 read_thread 单次最多 10 turns、单 item 输出最多 20,000 chars；它天然比 Code Pet Provider 的 256 KiB 单工具文本上限更保守。

2.3 WebSocket 压缩口径

  • Host 与 Remote 实际协商 permessage-deflate，双方都启用 server_no_context_takeover 和 client_no_context_takeover；每条消息使用独立字典。
  • 复测按 yawc/flate2 的默认 Deflate 级别，对完整 JSON-RPC UTF-8 消息执行 raw DEFLATE + Z_SYNC_FLUSH，按 RFC 7692 移除末尾 00 00 ff ff，再加入服务端 WebSocket frame header。
  • “压缩后 WSS wire”包含压缩 payload 和 WebSocket frame header，不包含 TLS record、TCP/IP header、ACK、重传和链路层开销；它是按当前协商参数得到的 wire-equivalent 计量，不是抓包值。
  • Gateway projection 与 Provider response 在这些样例中没有 Provider extension 正文；复测以完整 Provider JSON-RPC response 作为 Gateway JSON 消息代理。该口径适合比较 payload，但不能替代真实移动网络吞吐/CPU profiling。

2.4 Provider Frame V1 口径

  • 旧 App 内 Provider 的 stdout 仍为 UTF-8 JSONL，wire bytes 是实际 JSON-RPC bytes 加换行；新源码构建 Provider 的 stdout 是实际读取到的二进制 Frame V1 bytes，不是压缩率推算。
  • Frame 固定 10-byte header：CPRF、version、encoding、big-endian payload length；V1 payload 固定为 JSON。小于 32 KiB 使用 raw，达到阈值后尝试 zstd level 1，只有同时节省至少 10% 和 1 KiB 才采用压缩。
  • 16 MiB 只检查 header 加编码后 payload。测试不设置解压后/JSON 尺寸上限，也不让 Runtime 截断内容；因此“JSON 大于某阈值但压缩 frame 合法”是设计允许的正常结果。
  • 新 Provider frame 在脚本中按 header 解析，并调用本机 zstd 解压后再校验 JSON-RPC。最终聚合证据保存为 reports/conversation-payload-benchmark-frame-v1-2026-09-05.json。

5. Provider Frame V1 最终实测：A-40 stdio wire 下降 91.3%

最终技术摘要：WebSocket 压缩只负责 Host→Remote；现在 Provider→Host 也由 SDK Runtime 使用独立的 Frame V1/zstd。相同 A-40 页从旧 JSONL 的 15,209,177 B 降至 1,329,231 B（-91.3%）。新领域 JSON 为 8,077,047 B，2,350 items 全部保留，传输层截断为 0。Provider 业务实现只返回强类型对象，不感知 frame、zstd 或尺寸检查。

5.3 历史阶段：为什么原始下降 48.6%，网络只下降 31.3%

旧协议里的 command/output 副本逐字相同，本来就是 Deflate 最容易压缩的数据。以 A-40 为例，旧消息从 14.51 MiB 压至 1.65 MiB（-88.6%）；删除重复并执行预算后，新消息从 7.46 MiB 压至 1.13 MiB（-84.8%）。因此压缩会“掩盖”一部分对象设计浪费，但不会消除解析、分配、序列化、Provider stdio frame 和 Host 内存中的原始成本。

8. 对象设计复盘：问题不是“字段多”，而是“同一事实有多个所有者”

修正后的架构判断：ToolInvocation 这个抽象本身是必要的；不合理的是它与 ConversationItem.contents 发生了完整正文所有权重叠，而且 tool 内部又有第二轮重叠。当前协议没有建立 single source of truth，因此服务端、客户端、截断器和增量同步各自选择不同字段都算“合法”，最终必然出现重复、分歧和补丁式 fallback。

8.4 最终协议决策：用判别联合让非法组合无法出现

最终方案不是在投影器里做文本去重，也不是为了工具抽屉建立另一套详情对象，而是直接修改 Provider/Gateway v1：ConversationItem、tool input 和 tool outcome 都采用带 kind 的封闭 oneOf。每个分支只拥有自己合法的字段，命令与输出各只有一个 canonical 位置。项目尚未现场发布，因此两个协议与两端实现同步更新，版本号仍保持 v1。

{
  "resource": { "itemId": "exec-…", "conversationId": "…" },
  "kind": "tool",
  "status": "completed",
  "title": "Shell",
  "tool": {
    "callId": "exec-…",
    "name": "shell",
    "input": {
      "kind": "command",
      "command": "rg …",
      "cwd": "/workspace"
    },
    "outcome": {
      "kind": "success",
      "contents": [{
        "contentId": "exec-…:output",
        "kind": "text",
        "text": "<唯一一份 output preview>",
        "truncation": {
          "originalBytes": 142362,
          "retainedBytes": 8192,
          "strategy": "head-tail"
        }
      }],
      "exitCode": 0
    }
  }
}
  • ConversationItem 联合：message、reasoning、tool/command、file change、approval、unknown 分支互斥；不再由一个对象上的大量 optional 字段表达领域状态。
  • ToolInput 联合：command | structured | opaque 三选一。Command 是“语义上执行命令”，Structured 是已可靠解析的 JSON，Opaque 是无法可靠理解的输入；尺寸大不等于 opaque。三种 input 均可携带同构 truncation，超长 command 使用 UTF-8 安全的 head-tail。
  • ToolOutcome 联合：success | failure 二选一。内容块是输出唯一所有者；结构化 JSON 作为一种内容块，不再同时写 text 与 structuredContent；错误 message 只保留短摘要。
  • 截断元数据属于内容：截断与抽屉无关。任意 UI 都读取同一内容块，并用 originalBytes、retainedBytes、strategy 显示它不完整。
  • Delta 指向 canonical content：继续使用 itemId + contentId；客户端 committed contentId 必须遍历各 item variant 的内容块，不能依赖文本相等。

8.5 实施边界：协议先行，传输细节止于 Runtime

  1. 先在 Provider/Gateway v1 Schema 固定联合、唯一所有权与截断元数据，并生成 Rust/Dart/TypeScript SDK。
  2. Provider Mapper 按新类型输出单份正文，并可在“原生 harness → 领域对象”阶段执行显式内容策略；Provider 实现本身只实现 generated trait 与业务分页。
  3. 共享 SDK Runtime 执行一次 JSON 序列化、raw/zstd 选择、Frame V1 封装和最终 encoded-frame 16 MiB 检查。它不认识 message/tool/preview，也不修改已经形成的响应。
  4. Host 使用同一个 SDK frame codec 读写，不重复实现压缩策略；Gateway 只做路由与边界投影，不探测、不裁切、不重试。
  5. Remote 更新解码、分页、committed contentId 和 delta 合并；消息内折叠或抽屉都只是同一 canonical 内容的视图。
不能采用的伪修复：只在 Host 投影器或 Remote 做文本去重不能从类型上排除双写；为抽屉建立第二份详情 payload 会重新制造双权威；让 Runtime 根据业务字段做页预算或静默截断，会把内容政策重新塞回传输层。WebSocket 压缩与 Provider Frame V1 分别保护两条物理通道，不能互相替代。

10. 方案状态：每一项对应什么真实案例

已完成 P0

方案 1：Remote 只在明确超限时按固定梯度缩页

对应案例：案例 A 的相同起点，40 turns 为约 14.4 MiB，20 turns 为 6.51 MiB，10 turns 为 3.47 MiB，1 turn 为 44.9 KiB。

最终行为：首个请求仍可取 40；只有稳定错误码为 provider_response_too_large 时，调用方才保持同一 cursor 按 40 → 20 → 10 → 5 → 1 重试。成功后沿用较小 limit 并推进 nextCursor，其他错误不重试，limit=1 仍超限则上抛。

为什么不在中间链路处理：Provider、Host 与 Gateway 不应猜测调用方希望牺牲页大小还是内容完整性。分页是 API 调用策略，Frame V1 只负责成功传输或明确拒绝。

验证：覆盖首帧和后续页超限、同 cursor 重试、成功后 limit 继承、非尺寸错误不重试，以及 limit=1 错误透传。

已完成 P0

方案 2：在 v1 协议层消除可共存的重复所有者

对应案例：案例 A 中 870 条命令的正文各出现 3 次；801 条输出各出现 2 次。精确重复正文至少 6,129,554 bytes。

实测结果：09-04 唯一所有权阶段在相同 A-40 页面上把完整 JSON-RPC 从 15,209,176 B 降到 7,819,655 B；最终共享 Agent 领域版为 8,065,684 B，但把 380 个截断降为 1 个。A-20/A-10/B/C 和列表都在共享类型后继续变小。

方案 4：用 Runtime Frame V1 替代响应内容预算

对应案例：870 个 command 中没有任何一个必须超过 256 KiB，但总 command item 达约 13.9 MB。单项阈值无法约束累计体积。

实测行为：SDK Runtime 对业务响应只序列化一次，按阈值选择 raw/zstd，再检查最终 frame。A-40 的 2,350 items 全部保留，8,077,047 B JSON 形成 1,329,231 B frame，没有任何传输层 truncation。

为什么删除 7 MiB：它按业务内容做传输降级，会产生阈值不连续、额外序列化和不可预测的信息损失。16 MiB 的目标只是保护 stdio 通道，因此只约束最终编码 frame 才与目标一致。

12. 已排除方向、未知项与下一步

已排除

  • “对话列表因为携带 Shell 原文而超限”：列表协议与本机实测均不支持该判断。
  • “只有某个超过 256 KiB 的巨型命令输出才会触发”：最大真实工具项均未触发 256 KiB 截断，累计已经接近 16 MiB。
  • “WebSocket 压缩可以直接解决 Provider stdio”：Deflate 只属于 Host→Remote；Provider→Host 需要独立的 Frame V1/zstd。最终实现后 stdio 上限按编码后 frame 判断，不再按压缩前 JSON 判断。
  • “Runtime 应按 7/5 MiB 内容预算截断 response”：这会混淆业务内容与通道保护，已经由最终设计删除。
  • “重复只是 Codex Mapper 的单点实现错误”：OpenCode 也发生双层填充，而 Claude 选择另一种放置方式，说明 Schema 缺少唯一事实源和跨 Provider 约束。

仍未知

  • 未确认 用户现场“列表超限”对应的确切 RPC method、Provider、cursor 和 response size；需要尺寸日志或原始错误上下文。
  • 未确认 Claude/OpenCode 在本机真实大历史中的重复数据规模；代码路径已确认，但尚未做与 Codex 案例 A 同口径的黑盒量化。
  • 已决策 当前没有现场发布兼容负担，Provider/Gateway 继续使用 v1，Code Pet 与 codepet-remote 同步升级，不维护旧字段双栈。
  • 未确认 长列表在多个 Provider 并发请求时，UI 是否把其中一个失败统一展示成“列表加载失败”。

后续顺序

  1. 在真机/WSS 上补 packet 或 transport byte counter，验证 TLS/TCP/VPN 后的实际传输量与解压 CPU。
  2. 加入只记尺寸、不记正文的接口观测，用 method、route、limit、raw/compressed bytes 和 truncation bytes 归因现场错误。
  3. 把 Remote “拉完全部历史”改成按需加载更早页面；当前超限缩页只控制单帧，超长会话总流量仍线性增长。
  4. 独立收口 conversation.list title/preview；列表 100 条压缩后约 56 KiB，当前不是历史超限根因。
最终判断：协议唯一所有权先消除了非法重复，Provider Frame V1 再独立压缩 stdio。相同 A-40 的最终业务 JSON 为 8,077,047 B，实际 zstd frame 为 1,329,231 B，相对旧 JSONL stdout 下降 91.3%，且 2,350 items 与正文没有被 Runtime 截断。Remote 的 40→20→10→5→1 只在明确超限时生效；Provider、Host 与 Gateway 不降级。对话列表 100 条的最终 frame 为 61,982 B，仍没有证据表明它与历史工具正文属于同一超限根因。Provider 开发者继续只实现强类型协议接口并调用 serve_stdio，无需理解物理帧。
